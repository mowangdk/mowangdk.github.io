# 工作

### tee

tee -a 的意思是：将从标准输入接收到的内容追加（Append）到一个或多个文件中，同时仍然将这些内容显示在标准输出（通常是屏幕）上。

```
2>&1 | tee -a /var/log/init.log
```


| 特性 | command > file 2>&1 | command 2>&1 \| tee -a xxx.log |
| --- | --- | --- |
| 屏幕输出 | 没有，所有输出都被“吸”进文件里了。 | 有，所有输出都会显示在屏幕上。 |
| 文件操作 | 覆盖 (Overwrite) 文件。 | 追加 (Append) 到文件末尾。 |
| 核心机制 | 纯粹的 Shell 重定向。 | 重定向 + 管道 (|) + 外部命令 (tee)。 |
| 主要用途 | 静默执行，只关心最终的日志文件（如后台任务、cron）。 | 实时监控并记录，既要看过程，也要保存结果（如安装、编译）。 |

### systemctl reload

测试的时候发现systemctl reload 会触发 fstab 里面的目录执行，比较好奇。从man 的输出来看有如下描述

```
daemon-reload

Reload systemd manager configuration. This will rerun all generators (see systemd.generator(7)), reload all unit files, and recreate the entire dependency tree. While the daemon is being reloaded, all sockets systemd listens on behalf of user configuration will stay accessible.

```

当然这些unit 进程还都是running 的，可能是 local-fs.target 支持了热升级吧



```bash
systemctl daemon-reload
systemctl start local-fs.target
```

这里的 `systemctl start local-fs.target` 看起来有点不寻常，但在这里有其特定的目的。

1.  **脚本的上下文**: 这个脚本在系统**已经运行**的情况下，手动地修改了 `/etc/fstab` 并添加了新的挂载点。
2.  **`systemctl daemon-reload`**: 这一步是必须的。它告诉 `systemd` 主进程：“配置文件（包括 `/etc/fstab` 被间接解析的结果）已经变了，请重新加载它们。” 这会让 `systemd` 识别到你新添加的那些条目，并为它们生成新的 `.mount` 单元。
3.  **`systemctl start local-fs.target`**:
    *   在正常的系统启动流程中，`local-fs.target` 是被自动“激活”的。
    *   在这里，`start` 一个 `target` 的意思是**“启动所有被这个 target ‘Wants’ 且当前尚未启动的单元”**。
    *   因为 `daemon-reload` 之后，`systemd` 知道了 `local-fs.target` 现在还“想要”新生成的 `.mount` 单元（比如 `data.mount`）。但这些单元当前是 `inactive` 的，因为系统已经启动过了，不会再自动触发它们。
    *   所以，执行 `systemctl start local-fs.target` 就会**触发 `systemd` 去启动所有那些新识别到的、属于 `local-fs.target` 但还未激活的 `.mount` 单元**。
    *   这实际上是一种巧妙的方式，来**模拟系统启动时的挂载流程，让 `/etc/fstab` 中所有未挂载的条目都被挂载上**，而不仅仅是你刚刚添加的那一个。

**与 `mount -a` 的对比**:
`mount -a` 命令也会读取 `/etc/fstab` 并挂载所有尚未挂载的条目。在功能上，它与这里 `systemctl start local-fs.target` 的效果非常相似。但使用 `systemd` 的命令有几个好处：
*   **一致性**: 保持了与 `systemd` 生态系统的一致性，所有操作都通过 `systemd` 来管理。
*   **依赖处理**: 如果新的挂载点有更复杂的依赖关系（虽然不常见），`systemd` 能更好地处理它们。
*   **日志记录**: 操作会被记录到 `journald` 中，便于统一排查。


### `local-fs.target` 的具体作用

`local-fs.target` 是 `systemd` 中一个非常重要的**目标单元 (target unit)**。理解它需要先理解 `systemd` 的两个核心概念：**单元 (Unit)** 和 **目标 (Target)**。

*   **单元 (Unit)**: `systemd` 管理的最小工作单元，可以是服务 (`.service`)、挂载点 (`.mount`)、设备 (`.device`)、目标 (`.target`) 等。
*   **目标 (Target)**: 一个特殊的单元，它本身不做任何具体工作，而是作为一组其他单元的**逻辑分组**。你可以把它想象成一个“同步点”或“里程碑”。当系统进入一个 `target` 时，意味着这个 `target` 所依赖的所有单元都已经被成功启动。

`local-fs.target` 的作用是：**标志着所有本地文件系统（定义在 `/etc/fstab` 中，且不是网络文件系统）已经被成功挂载**。

#### 工作流程：

1.  **系统启动**: 在系统启动的早期阶段，`systemd` 会开始处理文件系统的挂载。
2.  **解析 `/etc/fstab`**: `systemd` 有一个 `systemd-fstab-generator` 工具，它会在启动时读取 `/etc/fstab` 文件，并为其中的每一个条目动态地生成一个 `.mount` 单元。
    *   例如，`/etc/fstab` 中的 `UUID=xxx /data ext4 defaults 0 0` 这一行，会被转换成一个临时的 `data.mount` 单元。
3.  **设置依赖关系**: 所有这些生成的本地文件系统的 `.mount` 单元，都会被自动地设置为 `local-fs.target` 的**一部分 (PartOf)**，并且 `local-fs.target` 会**依赖于 (Wants/Requires)** 它们。
4.  **达到目标**: `systemd` 会并行地启动所有这些 `.mount` 单元（即执行挂载操作）。只有当**所有**这些本地文件系统的挂载操作都成功完成后，`systemd` 才会认为 `local-fs.target` 这个“目标”已经达成。

你可以通过 `systemctl show` 命令来查看 `local-fs.target` 依赖了哪些单元：
```bash
systemctl show -p "Wants" local-fs.target
```
你会看到一长串的 `.mount` 单元列表。

#### 它在启动顺序中的位置

`local-fs.target` 是一个非常基础和早期的目标。很多其他重要的服务，比如数据库服务、Web 服务器等，都需要在文件系统准备好之后才能启动。因此，这些服务的 `.service` 文件中通常会包含这样的指令：

```ini
[Unit]
Description=My Web Server
After=network.target local-fs.target  # <--- 在网络和本地文件系统都就绪后才启动
```
这确保了当 `My Web Server` 启动时，它所需要的所有本地目录（如日志目录、数据目录）都已经可用。
